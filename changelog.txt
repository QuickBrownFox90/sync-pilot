== Changelog ==

= Version 0.2.3 =

* Security: The error log (the option `syncpilot_error_log`) grew without a limit, was loaded on every request of the whole site (autoload), and on a wrong signature `log_error()` wrote the complete request into it with `print_r()`, SQL rows of the upload included. The public endpoints write to the log before the signature is known to be right, so anyone could fill the option with requests of any size and slow the site down. Now the log keeps only its newest 100 KB (`LOG_MAX_BYTES`, the oldest entries go first, it always starts with a whole entry), one entry is at most 4 KB, and the option is stored without autoload. The data of a request is described and no longer copied: names and sizes, the beginning of short values, and `sig`, `key`, `nonce`, `chunk`, `form_data`, cookies and passwords are not logged at all (only their size); the body of a remote answer is cut to its beginning with its size, and the size of the request is logged. An old log of an installation is cut and stored without autoload once (`trim_error_log()` on `init`, it costs no query when there is nothing to do)
* Added: Updater (`class/syncpilot-updater.php`): SyncPilot finds new versions in the GitHub releases (pre-releases included) and offers them as a normal plugin update, with the dialog "View details" and a link "Check for updates" in the row of the plugin. It takes only the `sync-pilot.zip` of the release from the repository itself, renames the unpacked folder to the plugin folder if it differs, caches a failed answer too, and asks GitHub only in the admin, in cron and in WP-CLI, never for a visitor. The constant `SYNCPILOT_DISABLE_UPDATER` and the filters `syncpilot_updater_enabled` and `syncpilot_updater_prereleases` switch it or the pre-releases off; German translation for the four texts
* Added: The checks that were made for the log and the updater are in `tests/` (run with `wp eval-file` on a test installation); the folder is not part of the ZIP
* Verified: The updater with a faked GitHub (27 checks: drafts, a foreign host or repository, a link without https, a tag that is no version and a ZIP with another name are ignored; the newest release wins by version; cache times; errors are cached; update data, "no update" entry, dialog with an escaped changelog, cache removed after a single and a bulk update, renaming of the folder), a visitor context (no request to GitHub, nothing cached) and the plugins page of a test install in a browser request (link "Nach Updates suchen", the link works with its nonce and answers 400 without it, notice after it)
* Verified: 14 checks on PHP 8.3 for the log (an entry of a 2.3 MB request is 410 bytes without row data, signature or key; a 3 MB error page and cookies of an answer; `WP_Error`; 1000 requests of 2.3 MB leave 100 KB; an old autoloaded log of 3.2 MB is cut to 100 KB without autoload and the second run does no query; clearing and reading), and over HTTP against a test install: six requests of 1.5 MB without a signature to the public endpoint added 2.6 KB to the log

= Version 0.1.2 =

* Security: The Media Files sync accepted paths from the other site without checking them. When a site received media files (`respond_to_push_request()`), the file was written to the uploads folder plus the path that the sender named, so anyone who knew the key could write any file, with any name, anywhere the web server may write — `../../wp-content/plugins/x/shell.php` gives code execution on the receiving site. Downloading (`process_pull_request()`) took the path from the list of the other site in the same way, and sending (`process_push_request()`) read the files named in the request. Now every path goes through the new `is_safe_media_path()`: relative to the uploads folder, no `.` or `..` segment, no absolute path or drive letter, no hidden file (`.htaccess`, `.user.ini`), only file types that WordPress allows for uploads (`wp_check_filetype()`, so also the types that a plugin adds), and no script extension inside a double extension (`image.php.jpg`, `.phtml`, `.phar`, `.cgi`, `.asp`, …). A second check, `is_inside_uploads()`, makes sure with `realpath()` that the destination is inside the uploads folder, symbolic links included. A request with one bad path writes nothing at all. New messages: "The path of the media file is not valid: %s (#111mf)", "The list of media files does not match the uploaded files. (#112mf)" and "The media file would end up outside the uploads folder: %s (#113mf)"
* Security: The three public endpoints of the Media Files sync (`syncpilot_mf_get_remote_media_listing`, `syncpilot_mf_push_request`, `syncpilot_mf_remove_local_attachments`) checked the signature but not the settings "Accept pull requests" and "Accept push requests"; a site that had both switched off still gave out its file list and accepted and removed files. They answer with the message "… configured to reject pull / push connections (#110)" now; the listing needs "pull" or "push" depending on what the other site wants to do and is refused without an intent
* Security: `ajax_process_chunk()` (public endpoint, signature checked afterwards) created a file in the temp folder with `wp_tempnam()` before it knew whether the request was signed, and left it behind when the upload failed, so unsigned requests could fill the temp folder. The upload is read in place now (`is_uploaded_file()`), PHP removes it itself at the end of the request, and an invalid compressed chunk is refused with #136 instead of being passed on as `false`
* Security: `backquote()` doubles backticks inside a name (`a``b`), so a name cannot break out of its quotes; the post types of the setting "Exclude post types" are escaped with `esc_sql()` before they go into the query of the export; the four `extract()` calls for the table names of the multisite joins are explicit assignments now
* Security: The URL parameter `syncpilot-profile` was written unchanged into the inline JavaScript of the admin page (`admin_head_connection_info()`), so a crafted link could run script in the session of an administrator who opens it (reflected XSS); it is cast to an integer now, and `get_profile()` treats everything that is not a saved profile number as the default profile (before, a non-numeric value raised a deprecation on PHP 8.3). The names of saved profiles and the saved find & replace values are escaped when the form is built
* Fixed: `ajax_plugin_compatibility()` raised a warning when the field `install` was missing
* Verified: 62 checks on PHP 8.3 and 8.4 — 36 paths that must be accepted or refused (`../`, absolute, Windows drive, backslashes, hidden files, `.php`, `.PHP`, `.phtml`, `.phar`, `image.php.jpg`, a null byte, no extension, `.sql`; accepted: `photo.jpg`, `logo.PNG`, `kontakt.pl.jpg`, umlauts, `.pdf`, `.zip`, `.sql.gz`), the destination check with a symbolic link that leads out of the uploads folder, the receiving endpoint (traversal, one bad path among good ones, a number of paths that does not match the files, a path through the link, no push permission), the permissions of the other two endpoints, three attacks against the real second site over HTTP with a valid signature (traversal with `.php`, double extension, absolute path — all refused, nothing created), and a real pull of 169 media files (9.7 MB) into a scratch folder with all sizes right and no script or hidden file created; no PHP message from the plugin
* Verified: The chunk upload against the real second site over HTTP (unsigned: refused with #130, signed plain and gzip: accepted, no temp file left); the export of options, posts, postmeta, comments and commentmeta with excluded post types and spam comments (the changed joins and the escaped post types), and the read-only probe of the admin page, the settings and the helpers, all without any PHP message from the plugin

= Version 0.1.1 =

* Security: **Both sites must run 0.1.1** — the request signature changed and 0.1.0 (or older) and 0.1.1 reject each other's requests with "Invalid content verification signature". The old signature was HMAC-SHA1 over all fields glued together without a separator, so a value could be moved from one field to another, and a recorded request could be replayed at any time. The new signature is `<timestamp>.<HMAC-SHA256>`; the HMAC covers the timestamp and every field with its name and the length of name and value, it is compared with `hash_equals()`, and a request is only accepted within 10 minutes of its timestamp (filter `syncpilot_signature_window`; the clocks of both servers must be roughly right)
* Security: The certificate of the other site is checked now — `remote_post()` passed `sslverify => false` on every request, and the setting "Enable SSL verification" was saved but never used. It follows the setting now, and new installations have it switched on (existing installations keep what they had stored). With the check on, a certificate error is reported with the new message "The TLS certificate of the remote site could not be verified … (#139)". The explanation of the setting in the Settings tab is rewritten, as it said that the check is off by default
* Security: The connection test no longer falls back from https to http when "Enable SSL verification" is on. Before, any failure of the https request — also one forced by someone on the network — switched the whole migration to unencrypted http and only showed the notice "SSL Disabled". With the check off the fallback and the notice stay as they were, so local sites without a certificate keep working
* Security: `unserialize()` creates no objects any more (`allowed_classes => false`, new helper `safe_unserialize()`) for answers of the other site, for `primary_keys` of a request, for media data and for every value that find & replace goes through. A manipulated answer or a manipulated value in the source database could otherwise start `__wakeup()` or `__destruct()` of any installed class (object injection). Find & replace now handles all objects like the objects of classes that are not loaded: the `(array)` cast keeps the property names, and the object is built again with its class name. Values in the old `Serializable` format (`C:…`) cannot be rebuilt without their class and are left unchanged
* Security: Text from the other site that the admin page shows with `.html()` goes through `syncpilot_sanitize_html()`: only `a` (with `href` to `#`, a relative path or http(s), plus `class`), `br`, `strong`, `b`, `em`, `i`, `u`, `code`, `p`, `ul`, `li`, `h3`, `span` and `div` (with `class`) stay, scripts, styles, event handlers and `javascript:` links are removed; the parser is `DOMParser`, which neither runs scripts nor loads images. Values of the other site that are plain text (plugin version, URL, table prefix, uploads path, media files version) are set with `.text()`
* Security: Export files (`…-migrate-…sql`, `…sql.gz`) in `uploads/sync-pilot/` can no longer be downloaded directly — an `.htaccess` (Apache) and a `web.config` (IIS) deny them, they are only handed out by the plugin after a login; the rules are also written into folders that already exist. Backups (`…-backup-…`) stay reachable, because the page links to them after a migration. The random part of the file names has 32 instead of 5 characters (`random_bytes()`), so that names cannot be guessed; older files keep working and are recognized when they are downloaded. The listing of the folder is switched off
* Security: Keys are generated with `random_int()` instead of `rand()`, and the character set contained no `w` and the `q` twice, now it has all 64 characters; keys that already exist are not changed
* Verified: 36 checks on PHP 8.3 and 8.4 for the signature (valid, wrong key, changed or added field, value moved between fields, old format, one hour old or in the future, garbage), `unserialize()` (no `__wakeup` or `__destruct` runs, arrays still work, objects in find & replace keep class and properties), the certificate handling (error message, no fallback with the check on, fallback with it off), keys and dump names; 18 checks of the HTML sanitizer in Chromium with script, `onerror`, `javascript:`, `data:`, `style`, `iframe`, form and broken markup, none of which ran or stayed, and with the real messages of the plugin, which stay intact; the rules of the dump folder against Apache: exports 403, backup 200
* Verified: Push and pull between two test installs with the new signature (client on the PHP 8.4 CLI, server on Apache with PHP 8.4, `WP_DEBUG` on both sides) ran without any PHP message from the plugin on either side; afterwards 86 of 87 tables had the same checksum as before (all posts, `wpml_language_switcher` and the font posts byte-identical), only `wp_options` differs in WordPress' own transients, the schedule (`cron`) and the rewrite rules; the remote site accepts a request with a valid signature and refuses — over real HTTP — the old signature, a valid but one hour old signature, a valid signature with a changed field and a missing signature
* Fixed: `finalize_migration()` ran `DROP TABLE` for every real table before it renamed the temporary table to its name, so a temporary table that was missing (a chunk that was lost) cost the real table. The order was suggested by the author of the plugin and is now: first it checks that all temporary tables exist and stops with the new message "These temporary tables do not exist … No table was replaced (#140)" if one is missing, then ONE `RENAME TABLE` renames all old tables to `_old_<name>` and all temporary tables to their final names (all renames succeed or none does, and the site never sees half a database), then the preserved options and the constraints are written, and only when all of that has worked the `_old_` tables are dropped. If a step after the renaming fails, the `_old_` tables stay as a backup; the next migration removes `_old_` tables it finds. Table names and prefixes with a backtick are refused with the new message (#141)
* Verified: `finalize_migration()` on throwaway tables (13 checks, PHP 8.3 and 8.4): everything works including a table that does not exist at the target yet; a missing temporary table stops with #140 and leaves every table untouched; an error after the renaming keeps the `_old_` tables with their data; the next run removes such leftovers and works; a backtick in a table name or prefix is refused. Against the real second site (Apache, PHP 8.4): a normal push and pull leave no `_old_` or `_mig_` table and give the same checksums as before (only `wp_options` differs in transients, schedule and rewrite rules); a push after which a temporary table was removed on the remote side was refused with #140, the 86 remaining temporary tables were still there and no real table, no `_old_` table and no data had changed
* Fixed: **0.1.0 breaks the whole admin page as soon as the migration form is shown.** `template/migrate-progress.php` called `$wpdb->get_prefix()`, a method that does not exist in WordPress, in the label of the progress bar. That is a fatal error: PHP stopped after the form, WordPress ended the page, and the footer with all SyncPilot scripts (`common.js`, `hook.js`, `script.js`, `media-files.js`) was never sent, so nothing on the page reacted — no radio button, no connection field, no "Migrate DB" button. The profile selection, the Settings tab and the export did not show it, because they do not render this template. The label shows the table prefix again (`wp_options`); the template had static text before 0.1.0
* Verified: The three views of the plugin page (profile selection, migration form for a new profile, migration form for a saved profile) answer with HTTP 200, a complete page, the four SyncPilot scripts and no PHP message; in a real browser (headless Chromium, logged in as an administrator, desktop size, real mouse clicks) the tabs switch, "Pull" and "Push" show the connection field, a pasted connection info is verified against the other site and fills in the search and replace rows, and a complete push through the interface runs to "Pushing to … completed" in 52 seconds without a JavaScript error or an HTTP error; afterwards the remote site has the same number of rows in all tables except `wp_options`, where exactly the 53 transients are missing that the form excludes by default, and no `_mig_` or `_old_` table is left
* Known issue: The signature does not protect against a replay within the 10 minutes, and `transfer_chunk()` still discards the answer of the remote site when no error was recorded on the local side (inherited from WP Sync DB 1.5; the damage it could do in `finalize_migration()` is gone)

= Version 0.1.0 =

* Security: The AJAX actions `syncpilot_cancel_migration`, `syncpilot_blacklist_plugins` and `syncpilot_plugin_compatibility` checked neither a nonce nor a capability, so every logged-in user, a subscriber too, could call them: cancelling with `intent=pull` and any `temp_prefix` dropped every table with that prefix — with `wp_` the whole site (verified on a test install with a subscriber account) —, and the other two let any user change which plugins are not loaded for SyncPilot requests and install or remove the MU compatibility plugin. All three now call `check_ajax_referer()` like the other actions (nonce plus the capability `export`, `manage_network_options` on multisite), and the JavaScript sends the new nonces `cancel_migration`, `blacklist_plugins` and `plugin_compatibility` (inherited from WP Sync DB 1.5)
* Security: `delete_temporary_tables()` refuses a prefix that is empty, that the real tables start with (`wp`, `wp_`) or that starts with the table prefix (`wp_posts`), so neither a request nor the signed cancellation from the remote site can drop real tables; temporary tables (`_mig_wp_…`) are not affected
* Fixed: Saving the plugin blacklist with no plugin selected raised an "Undefined array key" warning and stored `null`; it now stores an empty list and only string values
* Fixed: If the SQL dump file could not be opened for writing (for example because the uploads folder is not writable), `stow()` and `close()` passed `false` to `fwrite()` / `fclose()`, which is a fatal `TypeError` since PHP 8 where PHP 7 only returned `false`; the export now ends with the error message "Failed to write the SQL data to the file. (#128)" again
* Fixed: `ajax_migrate_table()` closed the dump file a second time after `transfer_chunk()` had closed it, which is a `TypeError` since PHP 8 whenever `end_ajax()` returns instead of exiting (WP-CLI migrations, tests); the file is only closed if it is still open
* Fixed: `apply_replaces()` read `replace_old` and `replace_new` of the form data without checking them, so a form without find & replace fields (a profile or a CLI call) raised two warnings and two `str_ireplace( null )` deprecations per processed row; missing fields now count as an empty list
* Changed: Code style of `class/syncpilot-base.php`, `class/syncpilot-media-files.php`, `compatibility/sync-pilot-compatibility.php` and `template/settings.php` like `class/syncpilot.php` before — more air between logical groups, aligned assignments, no braces around single statements, an early `return` instead of `else` in `open_ssl_enabled()`; no functional change (compared token by token with the previous version)
* Changed: Code style of the JavaScript and CSS files and of the other templates in the same way (not compared token by token, the files are syntax-checked)
* Changed: The version is raised to 0.1.0 in the plugin header, in `$GLOBALS['syncpilot_meta']`, in the MU compatibility plugin and in the README
* Changed: The status in the README no longer says "functionally identical" to WP Sync DB 1.5 and names the fixes and the open points instead
* Verified: All PHP files lint without errors or deprecations on PHP 8.1, 8.2, 8.3 and 8.4; on a test install with `WP_DEBUG` on PHP 8.3 and 8.4 the Migrate page with all tabs, the diagnostic info, the SQL export (plain, gzip, find & replace of the site URL, excluded post types, excluded spam comments), the local backup stage and the import of a chunk run without any PHP message from the plugin
* Verified: A complete push and a complete pull over HTTP between two test installs (client on the PHP 8.4 CLI, server on Apache with PHP 8.4, `WP_DEBUG` on both sides, chunks gzip-compressed, remote backup stage, find & replace of the site URL and the file path, `keep_active_plugins`) ran without any PHP message from the plugin on either side; after the push all 87 tables had the same number of rows as the source, the remote kept its own settings, key, URL and active plugins, and after the pull back the source install had the same checksums as before for posts, postmeta, terms, users and comments
* Fixed: Find & replace changed values that contain none of the search strings, because every value was unserialized and serialized again or JSON-decoded and encoded again: JSON lost its spaces and got `\/` for every slash (for example the `wp_global_styles` and `wp_font_family` posts), and serialized objects of classes that are not loaded during the migration came back with public copies of their private and protected properties (the option `wpml_language_switcher` grew from 2841 to 5277 bytes, `O:19:"WPML_LS_Footer_Slot":2:{…}` became `:4:{…}`). `recursive_unserialize_replace()` now returns a value unchanged if the new `contains_search_term()` finds none of the search strings in it — also not in JSON notation (`http:\/\/…`), ignoring case like `str_ireplace()`, and including the domain that subdomain multisite installs replace (inherited from WP Sync DB 1.5, identical on PHP 7.4 and 8.0 to 8.4)
* Fixed: Serialized objects of a class that is not loaded (`__PHP_Incomplete_Class`) and that contain a search string are now processed through an `(array)` cast and built back into the same object, so private and protected properties keep their names and no public copies are added; the class name itself is never replaced
* Fixed: JSON values that contain a search string keep the escaping of the original text — `json_encode()` only writes `\/` and `\uXXXX` if the original value used them; before, every replaced JSON value got escaped slashes and unicode (for example the font URLs of the `wp_font_face` posts)

Before the fixes the global styles and font posts and `wpml_language_switcher` had changed without anything being replaced in them
* Known issue: `transfer_chunk()` discards the answer of the remote site when no error was recorded on the local side, so an error in `process_chunk()` on the remote site is not shown, and `finalize_migration()` runs `DROP TABLE` for the real table before `RENAME TABLE` of the temporary one. If a chunk got lost, the finalize step then drops a table without replacing it (inherited from WP Sync DB 1.5; seen only with a test script that reused one plugin object for all requests)
* Known issue: Not yet verified on PHP 8.2+: the Media Files sync, multisite and the WP-CLI integration
* Known issue: A security review found more hardening items that are not fixed yet and that are inherited from WP Sync DB 1.5 — the TLS certificate of the other site is never verified (`sslverify` is fixed to `false`, the setting "Enable SSL verification" has no effect) and the connection test can fall back from HTTPS to HTTP, `unserialize()` is used on answers of the other site, SQL dumps in `uploads/sync-pilot/` are not protected against direct download, some messages of the other site are written into the admin page with `.html()`, and the request signature (HMAC-SHA1 without a timestamp, fields joined without a separator) and the key generation (`rand()`) are weak; until they are fixed, use SyncPilot only between sites you control and only over a trusted connection

= Version 0.0.1 =

* Added: First test release of SyncPilot (private, version 0.0.1; the first public release is planned as 1.0.0 once the changes of the 0.x versions have been tested on several installs) — a fork of WP Sync DB 1.5 (itself a continuation of WP Migrate DB by Delicious Brains, last maintained in 2014) merged with WP Sync DB Media Files 1.1.4b1; functionally identical to those two plugins, rebranded and merged into one
* Changed: The Media Files addon is now part of the plugin — `SyncPilot_Media_Files` extends `SyncPilot_Base` directly and is loaded by `sync-pilot.php` right after the core class, so the migration form, the "Media Files" option and the AJAX handlers are always available; the `WPSDB_Addon` class (`class/wpsdb-addon.php`), the addon registry in the base class (`$this->addons`, `is_addon_outdated()`), the "addon out-of-date" admin warning and the second plugin header with its `version.php` are removed, as there is no separate addon whose version could mismatch
* Changed: Everything is renamed from `wpsdb` / `wp-sync-db` to `syncpilot` / `sync-pilot` — classes (`SyncPilot`, `SyncPilot_Base`, `SyncPilot_Media_Files`), functions, option names (`syncpilot_settings`, `syncpilot_error_log`), AJAX actions (`wp_ajax_syncpilot_*`, media files: `syncpilot_mf_*`), nonces, filters and actions, the `$GLOBALS['syncpilot_meta']` array, JS variables and script handles, CSS classes, the admin menu slug (`page=sync-pilot`), the text domain and the file names (`sync-pilot.php`, `class/syncpilot*.php`, `compatibility/sync-pilot-compatibility.php`, `languages/sync-pilot-en.pot`); this is a deliberate clean break, so both sides of a migration need SyncPilot and a remote site still running WP Sync DB cannot be reached
* Changed: The media files script is enqueued as `sync-pilot-media-files` — a plain rename would have given it the same handle as the core script (`sync-pilot-script`), which would have made it depend on itself and never load; the media files options form moved from `template/migrate.php` to `template/media-files-options.php` and its script from `asset/js/script.js` to `asset/js/media-files.js`
* Added: One-time import of WP Sync DB settings — on the first load `SyncPilot_Base::migrate_legacy_settings()` copies the `wpsdb_settings` option (API key, pull/push permissions, saved profiles, plugin blacklist) to `syncpilot_settings` if the latter does not exist yet, and records the time in `syncpilot_legacy_migrated`; the old option is only read, never changed or deleted, so WP Sync DB can stay installed side by side until the switch is complete
* Changed: Plugin header — author, `Requires PHP: 8.1`, `Requires at least: 6.0`, `Domain Path`; the plugin title shown in the admin is now fixed to "SyncPilot" instead of being derived from the file name; the MU compatibility plugin (`sync-pilot-compatibility.php`) is renamed, so a compatibility plugin installed by WP Sync DB (`wp-sync-db-compatibility.php`) is not replaced and keeps acting only on `wpsdb*` requests
* Changed: Help tab — the support link points to the author's website instead of the GitHub issue tracker of the original project; the demo videos are still the original screencasts of WP Sync DB and show its old user interface
* Removed: `github-updater` installation instructions and the `GitHub Plugin URI` header of the original plugin; `composer.json`, `composer.lock` and `vendor/` (only `composer/installers`) of the Media Files addon, which are not needed at runtime
* Added: Release workflow (`.github/workflows/release.yml`) — publishing a GitHub release builds `sync-pilot.zip` with the correct `sync-pilot/` root folder and attaches it to the release; the workflow refuses to build if the version in the plugin header differs from the release tag
