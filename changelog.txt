== Changelog ==

= Version 0.4.4 =

* Changed: Exports and backups are put into a folder of their own with a name that cannot be guessed: `uploads/sync-pilot/exports-<16 characters of wp_hash('syncpilot-exports')>/` (`get_upload_info()`), the same kind of name as the folder of the dumps for the import. Before, they were in the folder of the plugin itself; the rule of that folder closed the exports (`-migrate-`) for the web server, but a backup was linked directly and could be fetched by anyone who had its address (the name has 32 random characters, but an address in a log, a mail or a browser history is enough). Nothing is written to the old folder any more. When the folder cannot be made, the path stays the one of the folder (it is reported as not writeable) instead of falling back to the uploads folder, which the web server hands out
* Changed: The rule of the folders (`protect_dump_directory()`, `.htaccess`, `web.config`, `index.php`) denies every `.sql` and `.sql.gz` file, in the new folder and in the old one (a rule of 0.4.3 is replaced when the folder is opened). Nginx reads neither file: the diagnostics tell it ("Export Folder Protected From The Web: NO - ... nginx: location ~ /exports-")
* Changed: An export and a backup are handed out by the plugin only (`download_file()`): the link of the page (`dump_download_url()`, also the address that is shown after an export that is kept on the server and after a backup) has a nonce (`syncpilot-download`), the name must be the name of an export or a backup (`-migrate-` or `-backup-`, 14 digits, the random part), the new folder is searched first and the old folder after it, the answer for a file that is not found is a 404 without the path of the server, a wrong nonce is a 403. An export is deleted after it was sent, as before; a backup stays. The header `X-Content-Type-Options: nosniff` is sent
* Changed: The list of the backups of the import (and `resolve_backup()`) reads both folders (`SyncPilot_Import::backup_paths()`), so the backups of the versions before can still be restored. `legacy_upload_path()` is the old folder; it is not used when a filter (`syncpilot_upload_info`) sets the folder
* Added: A link "Remove" behind every backup of the restore list (`SyncPilot_Import::delete_backup()`, `ajax_import_delete()` with `source=backup`, the same nonce as for a dump), after a question in the dialog of the page. A backup that was written less than two minutes ago is not removed (a migration may still be writing it; the filter `syncpilot_import_backup_min_age`), and neither is the file of an import that is under way. Only a file with the name of a backup in the folder of the exports (or the old folder) can be removed
* Added: A guard for an older PHP at the top of `sync-pilot.php`: when the request runs a PHP before 8.2 (`syncpilot_php_too_old()`), no class of the plugin is loaded and the admin gets a notice with the version that runs and the one that is needed (`syncpilot_php_notice()`), instead of a parse error on the first class (`enum SyncPilot_HelpCode` needs PHP 8.1) that stops the whole page. The part of the file above the guard is written for PHP 5. This happens when a WordPress is reachable under several domains that are vhosts of their own (Plesk): every domain has its own PHP version, so the same files run under 7.x on one domain and 8.2 on another; the plugin header only stopped the activation, not the load. Checked under PHP 7.3, 7.4, 8.0 and 8.1 (the notice) and 8.2 (loaded)
* Added: The diagnostic info has "Export Folder" and "Export Folder Protected From The Web" (YES is the good answer; the line of the import folder, "Import Folder Reachable" since 0.4.0, is renamed the same way, because "Reachable: No" read as if the plugin could not reach its folder; a harmless probe file is put into the folder, asked for by its address and removed); `SyncPilot_Import::is_reachable()` takes the folder and the extension of the probe
* Added: `tests/php-guard.php` (the check of the version, the notice, and with the tokens of PHP that the part above the guard has no newer syntax) and `tests/release-check.mjs` checks that the guard comes before the first `require` and that its minimum is the one of the header, `tests/export-folder.php` (the folder, the rule, the old rule replaced, the links, both folders, the folder that cannot be made) `tests/import-backup.php` and `tests/browser/import.mjs --restore` (the removal of a backup: the question, a cancel, a backup that is too new, the removal) and `tests/browser/download.mjs` (an export through the interface: the link, the file is not served by the web server, a wrong nonce, a name that is no export, the file is handed out once, a gzip export). `push.mjs` and `import.mjs` look for the backup files in the new folder

= Version 0.4.3 =

* Added: A backup and an export of SyncPilot have a line for programs in their head: `# syncpilot-header: {"format":1,"kind":"backup","version":"0.4.3","created":"2026-11-20T12:29:09Z","home":"https://...","prefix":"wp_","multisite":false,"server":"11.8.6"}` (`db_backup_header( $kind )`). The lines for a person are in the language of the site and say nothing of the kind of the file, the address or the prefix; this line has no language and no key. The kind says backup or export, the time is UTC, `home` and `prefix` are those of the site that wrote the file (a backup of the other site of a push is written by that site, so it has its address)
* Added: The last table of a backup or an export is followed by the mark `# syncpilot-end: {"complete":true,...}`, the last line of the file. A backup of a migration that stopped (or was cancelled) before its last table was written does not have it, so it is known to be incomplete
* Added: A backup of SyncPilot is restored with the import: the dump box has a third choice "Restore a backup" with the list of the backups of the folder of the backups and exports (`SyncPilot_Import::backups()`: the files with the name of a backup, `<database>-backup-<14 digits>-<32 characters>.sql`, newest first, no link; the file is read in place, nothing is copied). Each entry has the time, the address when it is not the one of this site, the size, and "not complete" when the end mark is missing; a backup of an older version has no head and is listed as "older backup, without details". The beginning and the end of a file are read for this (`backup_info()`, the mark must be the last line of the file, so a line like it in a value of the data does not count). The import reads a backup as it is: the head is a comment, and the tables, the DROP TABLE and the INSERT of a backup are what it knows (a backup of today: 277 statements, none refused). No automatic backup before a restore, as for every import: the option for a backup decides
* Added: A backup that is not complete is restored only after a question in the dialog of the page and when the start says so (`confirm_incomplete`); without it the start is refused with the new help code 308 `ImportBackupIncomplete`. The choice "Remove the file after the import" is not offered for a backup and the file of a backup is never removed (`state_file_path()`, `source` in the state, `resolve_backup()` checks the name like `resolve()`). The log of the start has `source` (folder or backup)
* Changed: "Remove" in the list of the dumps asks in the dialog of the page like the other questions, not with the pop-up of the browser (0.4.2 used `window.confirm()` and `window.alert()` there)
* Added: `tests/import-backup.php` (the head, the end mark, the list, the way from a name to a file, the start of an incomplete backup) and `tests/browser/import.mjs --restore` (an import with a backup, then the restore of that backup from the list: every table of the first site is as before)

= Version 0.4.2 =

* Added: A dump can be uploaded in the page. The dump box of the import has a choice "Choose a file from the folder" / "Upload a file"; the upload sends the file in parts of the size of one request (the setting for the size of a request, `syncpilot_max_request`, one MB by default), as a file of a form, so the limits of PHP for the size of an upload and of a post (`upload_max_filesize`, `post_max_size`) are the limits of a part, not of the dump. `ajax_import_upload()` (nonce `import_upload`) puts the parts one after the other into a file of the folder `.upload` inside the folder of the dumps (named by the ID of 24 hexadecimal characters that the page makes); a part must begin where the file ends, so a part that came twice or not at all is told to the page (`received`), which goes on from there; the page sends a part again up to three times after an error of the connection. The first part checks that the disk has room (the size of the file and 64 MB, the filter `syncpilot_import_free_bytes`); the last part checks that the file is not empty and that a gzip file is one (by its content: the name and the content must agree) and moves it into the folder of the dumps. A file that is not finished is removed after a day (`remove_stale_uploads()`, run by the first part of an upload and by the list; the filter `syncpilot_import_upload_max_age`); cancelling the upload removes it at once. New help code 307 `ImportUploadFailed` (the log has the reason: id, folder, disk, offset, chunk, write, name, empty, gzip; never the name of the file or its content)
* Added: A .sql file is compressed in the browser before it is sent (`CompressionStream`, gzip, as a stream: the file is not held in memory) when the box "Compress a .sql file before the upload" is checked (it is by default) and the browser can. The file is smaller (often a tenth), and a firewall in front of the site sees binary data, not SQL: a post with SQL in it is what some firewalls block. The server gets the original name and makes it `.sql.gz`. A file that is gzip already is sent as it is
* Added: A name for an uploaded file: what the browser calls the file is cleaned (letters, digits and `. _ ( ) -` stay, the rest becomes a dash, a folder in it is cut off, at most 100 characters) and gets `-u` and eight random hexadecimal characters before the extension (`kunde-u1a2b3c4d.sql.gz`). The random part cannot be guessed and keeps two uploads of the same file apart; it also tells an uploaded file from one that was put into the folder (`is_uploaded_name()`, `uploaded` in the list)
* Added: The choice "Remove the file after the import" (`delete_file` of the start of the import, not saved in the profile because it depends on the file): it is on when an uploaded file is chosen and off for a file that was put into the folder by hand, and can be changed. The file is removed by `finalized()` after the tables are replaced, so a cancel, a stop and an error leave it; the log has "Import file removed"
* Added: A link "Remove" behind every file of the list removes it from the folder after a question (`ajax_import_delete()`, nonce `import_delete`; the file of an import that is under way is refused)
* Added: `tests/import-upload.php` (names, uploaded or put there, parts that were not finished, the removal, after the import and after a cancel) and `tests/browser/import.mjs --upload` (the file is chosen with a file input by CDP and sent in parts of 64 KB, compressed or not with `--plain`, a gzip file with `--gzip`; the content in the folder is compared with the file, the choice for the removal, the import, and the file is gone afterwards). German texts added

= Version 0.4.1 =

* Changed: A push and a pull replace in serialized values the way the import does since 0.4.0. `export_table()` calls the new `SyncPilot::replace_value()` instead of `recursive_unserialize_replace()`: a serialized value is rewritten without unserializing it (`rewrite_serialized()`, moved from `SyncPilot_Import` to `SyncPilot_Base`), so an object that is used twice is no longer copied (an object graph of 764 bytes with a depth of 18 needed 22 MB and 669 MB of memory, every level doubles it), references (`r:` and `R:`) stay references and the integer keys of an `ArrayObject` stay integers. What cannot be read to the end (plain text, JSON, a damaged serialized text) goes to the old function as before. For the data that the old function could handle the result is the same. `replace_value()` is public in `SyncPilot`; the one of `SyncPilot_Import` calls it
* Added: A push and a pull replace a collation or character set that the receiving database does not know by a similar one. The tables of MariaDB 11 have `utf8mb4_uca1400_ai_ci`, the ones of MySQL 8 `utf8mb4_0900_ai_ci`; an older database refused the first `CREATE TABLE` ("Unknown collation") after the backup and left the temporary tables. `process_chunk()` runs every `CREATE TABLE` through the new `SyncPilot::map_collations_in_query()` (a pull: this site, a push: the other site, which needs 0.4.1 for it), the rules are the ones of the import (`map_collation()`: binary stays binary, the others become `utf8mb4_unicode_520_ci` or the next of their kind, `utf8mb3` and `utf8` are mapped to each other). There is no option: a CREATE TABLE with known collations is not touched, so nothing changes when all is known. The log has "Collation mapped" for every table that was changed, with the table and the names. The functions `mask_literals()`, `used_collations()`, `unsupported_collations()`, `map_collation()`, `map_charset()`, `known_collations()` and `apply_collation_map()` moved from `SyncPilot_Import` to `SyncPilot_Base` (the import uses them as before)
* Added: The choice "Keep the collations of the tables on the other site" for a push (`keep_collations`, saved in the profile, off by default, offered only for a push). Without it the tables arrive with the collation they have on this site, which after a pull from a newer database (MariaDB 11 to an older one, then a push back) replaces `utf8mb4_uca1400_ai_ci` of the live site by `utf8mb4_unicode_520_ci`, and a database with mixed collations can answer a JOIN with "Illegal mix of collations". With the choice the other site (`keep_collations_in_query()`, called from `map_collations_in_query()`) gives a table that exists the collation of the table and of its columns, and a table that is new the collation of its posts table (a binary column stays binary); only where the character set is the same, because another one could cut the data. The field is sent and signed with the chunk only when the choice is made (a site before 0.4.1 could not check the signature of a chunk with an unknown field). The log has "Collation kept" with the table, whether it is new, and what was changed. There is no such choice for a pull yet. `split_code()` (`SyncPilot_Base`) cuts a statement into code and strings
* Fixed: `apply_collation_map()` also changed the text of a string in the CREATE TABLE (a comment of a column or a `DEFAULT` that says `COLLATE <name>`). Only the code between the strings and the names in backticks is changed now
* Added: `tests/replace-compare.php` runs the old and the new replace over every value with a search term on a real installation (`wp eval-file tests/replace-compare.php <search> <replace> [more pairs] [--max-old=BYTES] [--all-tables]`), writes nothing and reports the values where they differ (table, column, key, the first place of the difference). `tests/collation-map.php` checks the mapping of a chunk, `tests/collation-keep.php` the choice to keep the collations, and `push.mjs --keep-collations` runs a push with it

= Version 0.4.0 =

* Added: The folder for dumps that are to be imported: `uploads/sync-pilot/imports-<16 characters>/` (`SyncPilot_Import`, new class in `class/syncpilot-import.php`). The characters are made from the salts of the site, like the name of the log file, so the folder cannot be guessed and needs no stored value; the filter `syncpilot_import_dir` sets the whole path, for example a folder outside of the web root. A dump (`.sql` or `.sql.gz`) is put there by the upload of the page or by hand (SFTP, a local copy). The folder is made with a rule that denies every request from outside (`.htaccess`, `web.config`, `index.php`): a dump holds the data of a site and is read by the import only. `files()` lists the dumps, the newest first; a file that cannot be used is listed with the reason (`name`, `extension`, `symlink`, `unreadable`, `empty`) so the page can say why it is not offered. `resolve()` is the one way from a name of the browser to a file: the name must be valid (no folder, no `..`, no name that starts with a dot), and the file must be a file of the folder itself, not a link. The AJAX action `syncpilot_import_list` answers the page with the list
* Added: The reader of dumps (`SyncPilot_Dump_Reader`, new class in `class/syncpilot-dump-reader.php`) gives a dump statement by statement, from any place of the file, with the memory of one block (1 MB) and the largest statement. A statement ends at a semicolon that is not in a string, a name in backticks, a comment or behind an escape, whatever the size of the blocks: a quote, `--`, `/*` or an escape that is cut between two blocks is handled. A `.sql.gz` is read with zlib (a gzip file is told by its content, not its name; going to a place in it reads from the start, a gzip file cannot be entered in the middle). A statement over 32 MB (the filter `syncpilot_import_max_statement_bytes`) or a file that ends inside a string stops the reading with the reason (`statement_too_large`, `unterminated`). The comments that only some servers run (`/*!40101 ... */`, `/*M!100616 ... */` of MariaDB) are opened when the server of this site runs them, as it does itself, and are comments for the others
* Added: What the import does with a statement is decided by `SyncPilot_Import::classify()`: DROP TABLE, CREATE TABLE, INSERT and the SET of the session (character set, checks, time zone, SQL mode) are run, the statements that only make the dump fast or safe in the program that wrote it (LOCK TABLES, transactions, DISABLE KEYS, USE, SET GLOBAL, the binary log) are skipped, everything else is refused (UPDATE, DELETE, TRUNCATE, GRANT, a trigger, a view, SELECT INTO OUTFILE, LOAD DATA, DELIMITER...). A table is a plain name of this database, never `db.name`; an INSERT or a CREATE TABLE with a SELECT in it, and a CREATE TABLE with a reference to another table or a file name, are refused. The word SELECT is looked for in the statement without its strings, names and comments (`mask_literals()`), so a post that says "select * from" is no reason. What is said of a refused statement has the kind (the first word, the second only when it is a word of SQL) and the reason, never a name or a value. The filter `syncpilot_import_allowed_variables` adds variables for SET
* Added: `with_table()` gives a statement another name for its table (the temporary prefix is put before the name this way), `used_collations()` the collations and character sets that a CREATE TABLE names, and `unsupported_collations()` those that this database does not know. A dump of MySQL 8 has `utf8mb4_0900_ai_ci`, which MariaDB and MySQL 5.7 do not have: it is found before the first table is made
* Added: A dump of the folder is scanned and loaded into the temporary tables (`ajax_import_start()`, `ajax_import_step()`, `ajax_import_cancel()`, nonces `import_start`, `import_step`, `import_cancel`). The start makes the ID of the migration (the log has "Migration started" with `intent` import, the size of the file and whether it is gzip) and the state of the import, kept in the folder of the log (`import-<ID>.json`, a transient is the fallback; one that a migration left is removed after a week). Every request of the browser works at the dump for `step_seconds()` (10 seconds, the filter `syncpilot_import_step_seconds`), at least one statement, and answers where it is (`phase`, `offset`, `total`, `statements`, `tables`, `done`): the phase **scan** reads the whole dump and writes nothing, so a statement that is not allowed (help code 302), a collation or character set that this database does not know (303), tables with another prefix than this site (305, unless the start says `other_prefix`), a file that is cut off or too large for a statement (304) are found before anything is changed; its answer at the end is the list of the tables (for the backup), the phase **load** (the request after the scan) removes the temporary tables of an earlier migration, makes the table for the ALTER queries and runs the dump on the temporary tables (`<temporary prefix><name>`), the phase **loaded** is the end. The log has "Import scanned" and "Import loaded" (statements, tables, bytes, seconds), and at verbose "Import step" for every request; an error stops the import, removes the temporary tables and the state, and ends the migration as "stopped" in the log; the totals of the tally (`queries_run`, `bytes_imported`) are kept as for a push. New help codes 301 `ImportFileInvalid`, 302 `ImportStatementRefused`, 303 `ImportCollationUnknown`, 304 `ImportReadFailed`, 305 `ImportPrefixDiffers`, 306 `ImportStateLost`; a statement that the database refuses is 152 `QueryFailed`, with the kind and table, never a value. A gzip dump is read from the start again by every request (a gzip file cannot be entered in the middle)
* Added: A gzip dump is unpacked once (phase **unpack**) into a copy in `.work/` in the folder of the dumps, when the disk has room for it (the size of the text plus 5 % and 64 MB, the filter `syncpilot_import_free_bytes`); the scan and the load read the copy, and it is removed when the load is over, when the import stops and when it is cancelled. Without room the gzip file is read as it is (every request from the start again) and "Import reads the gzip file itself" is written at the level verbose. A gzip file that is cut off ends early without an error from zlib: the size it says at its end (`gzip_trailer()`) is compared with what was unpacked, help code 304 `ImportReadFailed`, reason `gzip_corrupt`
* Added: The find and replace (phase **replace**, the request after the load). The form of the migration (`form_data` of the start) has the rows to find and replace and the choice for the GUIDs, and every value of the temporary tables goes through `recursive_unserialize_replace()`, the function that a push or a pull uses for every value, so serialized data and JSON stay valid and the text in them keeps its length. The database finds the rows (a `LIKE` over the columns with text, also for the slashes of JSON written as `\/`), they are read in the order of the primary key (a key of several columns is fine), 100 at a time (the filter `syncpilot_import_replace_rows`), and written back one by one; a table without a primary key is read in the order of the database and every column is compared when a row is written. The GUID of a post is left alone unless `replace_guids` is set. Without a find and replace row the phase is over at once. The log has "Import replaced" (tables, rows looked at and changed, seconds). `SyncPilot::set_migration_form_data()` hands the form to the function. The domain and the path of a multisite network (`wp_site`, `wp_blogs`) are values like all others: they are changed by rows of find and replace (the domain without `//` as a row of its own); the rules of a pull for the network and for subdomains (`apply_replaces()`) do not apply
* Added: What the SET statements of a dump set belongs to the session, and the next request of the import has a new connection: when a request ends the values of the variables that the dump has set (the character set, the time zone, the checks, the variables of the user such as `@saved_cs_client` and `@OLD_SQL_MODE`) are read and set again by the next one (`import_capture_session()`, `import_restore_session()`). Without it a request that begins between the two SET statements of a table sets `character_set_client` to NULL and the import fails, and the time zone of the dump is lost
* Added: A dump of MariaDB wraps every table in `SET AUTOCOMMIT=0` ... `COMMIT`. A statement that sets AUTOCOMMIT is skipped, and the import commits every query: what is not committed when a request ends is lost with its connection
* Added: The import is a choice of the form of its own (the template `migrate.php`, `modules/import.js`). The choice of the dump takes the place of the connection data: the folder, the list of its files with size and date (a file that cannot be used is listed with the reason), a refresh link, and the checkbox for tables with another prefix (`other_prefix`). What does not belong to an import is hidden (the choice of the tables, the filters of the source: post types, spam, transients, the media files, the kind of backup); the rows of find and replace are turned like for a pull, so that this site is the new value and the old value (the address and the path in the dump) is typed in. The form needs a dump (`form_is_valid()`), and the profile saves `import_file` and `import_other_prefix`. German texts added
* Added: The requests of the import in the progress box (`start_import()`, `import_step()`): unpack, check, the backup of the tables of this site that the dump replaces (when chosen: the same loop of the tables as for a pull, `start_tables()` is exported and `set_after_backup()` says that the load follows it, and the backup file is named by `ajax_import_start()`), load, replace, then the tables are replaced like after a pull (`finalize_migration()` also for the intent `import`, nothing is sent to another site, the state of the import is removed by the action `syncpilot_migration_finalized`). Pause and cancel work as for the other migrations: a cancel removes the state, the unpacked copy, the temporary tables and the backup (`SyncPilot_Import::cleanup()`, the intent `import` in `ajax_cancel_migration()`). The end entry of the log has `intent` import, the seconds of the parts and the totals
* Added: A collation or character set of the dump that this database does not know is replaced by a similar one instead of stopping the import (found with a dump of MariaDB 11 that has `utf8mb4_uca1400_ai_ci` on an older database; a dump of MySQL 8 has `utf8mb4_0900_ai_ci`). `map_collation()`: a binary collation stays binary, the others become `utf8mb4_unicode_520_ci` (what WordPress uses) or the next of their kind, `utf8mb3` and `utf8` are mapped to each other (`map_charset()`). The scan makes the map (`collation_map` in the state), the load applies it to every CREATE TABLE behind COLLATE, COLLATE=, CHARSET= and CHARACTER SET (`apply_collation_map()`), "Import scanned" in the log has `collations_mapped`. A collation that has no match (its character set is not known either) still stops the import (303). The checkbox "Stop when the dump has a collation that this database does not know" (`strict_collations`, saved in the profile as `import_strict_collations`) switches the mapping off. German text added
* Added: The replace of the import does not unserialize serialized values (found with a real dump: the replace ran out of memory in `unserialize()` at a limit of 4 GB). The function of a push or a pull (`recursive_unserialize_replace()`) unserializes a value and builds it again, and it copies every object that is used twice in it: a serialized object graph of 764 bytes with a depth of 18 became 22 MB and 669 MB of memory, every further level doubles it, and the references are lost afterwards (it also turns the integer keys of an `ArrayObject` into strings). The import rewrites a serialized value without unserializing it now (`rewrite_serialized()`): the text is read once and written again, the strings that are values get the replacement and their new length, keys, class names, numbers, references and custom serialized data are copied as they are, a serialized text in a string and a value that is JSON are treated as before. The memory is the size of the text twice, and a graph of 1644 bytes with a depth of 40 takes 0.2 ms. A text that is not read to the end is left to the old function. For data that the old function can handle the result is the same (checked against it on every row of a real dump). The pull and the push still have the old function
* Added: The replace reads the rows of a batch within a memory budget: 100 rows of 3 MB do not fit into a limit of 96 MB (the buffered result is held twice). The rows are read one by one from the database now and the reading of a batch stops at a budget of a twelfth of the free memory (at most 16 MB, at least 1 MB, the filter `syncpilot_import_replace_bytes`), at least one row; the next request goes on from the last row (`read_rows()`)
* Changed: The choices of the form are in the order Pull, Push, Import, Export (before: Export, Pull, Push). The default of a new profile is still the export
* Added: The diagnostic info has two lines for the folder of the dumps: `Import Folder` and `Import Folder Reachable`. `is_reachable()` puts a harmless file with a random content into the folder, asks for it by its address in the uploads folder and removes it; the answer is `YES` when the web server hands it out (nginx ignores the `.htaccess` of the folder and needs a rule of its own), `No` when it does not, `Unknown` when the folder has no address (outside of the uploads folder) or the request fails. For this `output_diagnostic_info()` runs the new action `syncpilot_diagnostic_info`, where other parts add their lines

= Version 0.3.4 =

* Fixed: The progress of a migration was `NaN%` and the blocks of the bar for the tables lay on top of each other when the site that holds the data runs MySQL 8 (seen on MySQL 8.4 with a multisite of 13 sites). `get_table_row_count()` read the name of the table from `$result['table_name']`, but MySQL 8 gives the columns of `INFORMATION_SCHEMA` in capitals (`TABLE_NAME`), so no table had a number of rows and PHP wrote a warning for each table. The query names its columns now (`AS "name"`, `AS "row_count"`), as `get_table_sizes()` always did. A table whose number of rows is not known counts as 1
* Fixed: The progress can no longer become `NaN` in the browser: `table_row_count()` in `progress.js` gives 1 for a table without a number of rows (0 stays 0, the blocks that are too narrow to be seen are added to the last table with it). It is used where the rows are summed (`draw_table_chunks()`, `count_progress()`)
* Fixed: The end entry of a migration ("Migration finished", ...) had wrong totals on the site that receives the data when all tables are migrated: `duration_s: 1` for a migration of 90 minutes and only the ALTER statements as `chunks_imported` and `queries_run`. The totals were kept in a transient, which is a row of the options table, and the options table is replaced by the migration, so the count began again after it. = Version 0.1.1 =

* Security: **Both sites must run 0.1.1** — the request signature changed and 0.1.0 (or older) and 0.1.1 reject each other's requests with "Invalid content verification signature". The old signature was HMAC-SHA1 over all fields glued together without a separator, so a value could be moved from one field to another, and a recorded request could be replayed at any time. The new signature is `<timestamp>.<HMAC-SHA256>`; the HMAC covers the timestamp and every field with its name and the length of name and value, it is compared with `hash_equals()`, and a request is only accepted within 10 minutes of its timestamp (filter `syncpilot_signature_window`; the clocks of both servers must be roughly right)
* Security: The certificate of the other site is checked now — `remote_post()` passed `sslverify => false` on every request, and the setting "Enable SSL verification" was saved but never used. It follows the setting now, and new installations have it switched on (existing installations keep what they had stored). With the check on, a certificate error is reported with the new message "The TLS certificate of the remote site could not be verified … (#139)". The explanation of the setting in the Settings tab is rewritten, as it said that the check is off by default
* Security: The connection test no longer falls back from https to http when "Enable SSL verification" is on. Before, any failure of the https request — also one forced by someone on the network — switched the whole migration to unencrypted http and only showed the notice "SSL Disabled". With the check off the fallback and the notice stay as they were, so local sites without a certificate keep working
* Security: `unserialize()` creates no objects any more (`allowed_classes => false`, new helper `safe_unserialize()`) for answers of the other site, for `primary_keys` of a request, for media data and for every value that find & replace goes through. * Changed: The status in the README no longer says "functionally identical" to WP Sync DB 1.5 and names the fixes and the open points instead
* Verified: All PHP files lint without errors or deprecations on PHP 8.1, 8.2, 8.3 and 8.4; on a test install with `WP_DEBUG` on PHP 8.3 and 8.4 the Migrate page with all tabs, the diagnostic info, the SQL export (plain, gzip, find & replace of the site URL, excluded post types, excluded spam comments), the local backup stage and the import of a chunk run without any PHP message from the plugin
* Verified: A complete push and a complete pull over HTTP between two test installs (client on the PHP 8.4 CLI, server on Apache with PHP 8.4, `WP_DEBUG` on both sides, chunks gzip-compressed, remote backup stage, find & replace of the site URL and the file path, `keep_active_plugins`) ran without any PHP message from the plugin on either side; after the push all 87 tables had the same number of rows as the source, the remote kept its own settings, key, URL and active plugins, and after the pull back the source install had the same checksums as before for posts, postmeta, terms, users and comments
* Fixed: Find & replace changed values that contain none of the search strings, because every value was unserialized and serialized again or JSON-decoded and encoded again: JSON lost its spaces and got `\/` for every slash (for example the `wp_global_styles` and `wp_font_family` posts), and serialized objects of classes that are not loaded during the migration came back with public copies of their private and protected properties (the option `wpml_language_switcher` grew from 2841 to 5277 bytes, `O:19:"WPML_LS_Footer_Slot":2:{…}` became `:4:{…}`). `recursive_unserialize_replace()` now returns a value unchanged if the new `contains_search_term()` finds none of the search strings in it — also not in JSON notation (`http:\/\/…`), ignoring case like `str_ireplace()`, and including the domain that subdomain multisite installs replace (inherited from WP Sync DB 1.5, identical on PHP 7.4 and 8.0 to 8.4)
* Fixed: Serialized objects of a class that is not loaded (`__PHP_Incomplete_Class`) and that contain a search string are now processed through an `(array)` cast and built back into the same object, so private and protected properties keep their names and no public copies are added; the class name itself is never replaced
* Fixed: JSON values that contain a search string keep the escaping of the original text — `json_encode()` only writes `\/` and `\uXXXX` if the original value used them; before, every replaced JSON value got escaped slashes and unicode (for example the font URLs of the `wp_font_face` posts)
* Verified: Round trip on the two test installs with these fixes — push from the source to the target and pull back with find & replace of the site URL and the file path: afterwards 86 of 87 tables of the source have the same checksum as before, including all posts, `wpml_language_switcher` and the font posts; in `wp_options` only `rewrite_rules` (regenerated by WordPress after the migration), WordPress' own transients and the `option_id` of the options SyncPilot keeps on purpose (`syncpilot_settings`, `syncpilot_error_log`, `active_plugins`) differ. Before the fixes the global styles and font posts and `wpml_language_switcher` had changed without anything being replaced in them
* Known issue: `transfer_chunk()` discards the answer of the remote site when no error was recorded on the local side, so an error in `process_chunk()` on the remote site is not shown, and `finalize_migration()` runs `DROP TABLE` for the real table before `RENAME TABLE` of the temporary one. If a chunk got lost, the finalize step then drops a table without replacing it (inherited from WP Sync DB 1.5; seen only with a test script that reused one plugin object for all requests)
* Known issue: Not yet verified on PHP 8.2+: the Media Files sync, multisite and the WP-CLI integration
* Known issue: A security review found more hardening items that are not fixed yet and that are inherited from WP Sync DB 1.5 — the TLS certificate of the other site is never verified (`sslverify` is fixed to `false`, the setting "Enable SSL verification" has no effect) and the connection test can fall back from HTTPS to HTTP, `unserialize()` is used on answers of the other site, SQL dumps in `uploads/sync-pilot/` are not protected against direct download, some messages of the other site are written into the admin page with `.html()`, and the request signature (HMAC-SHA1 without a timestamp, fields joined without a separator) and the key generation (`rand()`) are weak; until they are fixed, use SyncPilot only between sites you control and only over a trusted connection
* Known issue: At the end of an export `get_alter_queries()` queries the table `{prefix}syncpilot_alter_statements`, which only exists if the schema has constraints; otherwise `wpdb` prints a database error when `WP_DEBUG` is on (inherited from WP Sync DB)

= Version 0.0.2 =

* Changed: The Help tab is reduced to a "Diagnostics" tab — only the diagnostic info and the error log with "Clear Error Log" remain; the support link and the demo videos (the original screencasts of WP Sync DB showing its old user interface) are removed together with their JavaScript and CSS; the template is now `template/diagnostics.php`, the tab hash is `#diagnostics` (was `#help`), and the error messages #105, #106, #108 and #118 point to the Diagnostics tab and the error log instead of "the Help tab for details on how to request support"
* Changed: The text domain is no longer repeated as a string literal in every gettext call but taken from the class constant `SyncPilot_Base::TEXT_DOMAIN` (`self::TEXT_DOMAIN` in classes and templates), so it can be changed in one line; the `Text Domain:` plugin header stays a literal, as WordPress reads it without executing PHP
* Added: German translation (`languages/sync-pilot-de_DE.po` and `.mo`, informal "du"); the source language is English
* Removed: `languages/sync-pilot-en.pot` — it was outdated and a template is not needed at runtime; the translations are shipped as `.po` and `.mo` directly
* Fixed: `e()` instead of `_e()` in the message "Could not delete the MySQL export file." would have ended in a fatal error "call to undefined function" if deleting the export file failed
* Fixed: The diagnostic info used the leftover text domain `wp-app-store` for "ext/mysqli" and "WP Memory Limit"
* Changed: The plugin header is written as a docblock with a leading ` * ` on every line and requires PHP 8.2 (was 8.1); the version is raised to 0.0.2 in the header, in `$GLOBALS['syncpilot_meta']` and in the MU compatibility plugin
* Fixed: `backquote()` used `each()`, which was removed in PHP 8.0 and would have ended in a fatal error if the function was called with an array; it now uses `foreach`
* Fixed: The diagnostic info called `mysql_get_server_info()` (removed in PHP 7) as a fallback when mysqli was not in use; the MySQL version now comes from `$wpdb->db_server_info()`
* Removed: Code for PHP's `safe_mode`, which does not exist since PHP 5.4 — the "PHP Safe Mode Enabled" notice (it never showed, because `$safe_mode = ini_get(…) && …` bound wrongly), the filter `syncpilot_hide_safe_mode_warning` and the `safe_mode` check before `set_time_limit()` (now only `function_exists( 'set_time_limit' )`)
* Removed: The "Internet Explorer Not Supported" notice and the script that showed it; the two strings are removed from the German translation
* Fixed: The status in the README named a version "2.0.0-dev" left over from an earlier draft; it now says 0.0.2 (alpha)
* Fixed: The release workflow read the version only from header lines that start with `Version:` and would have refused to build after the header got the leading ` * `; it now accepts both forms
* Changed: Code style of `class/syncpilot.php` — more air between logical groups, aligned assignments, no braces around single statements; no functional change
* Known issue: Not everything is translatable yet — the words "local" and "remote" that the JavaScript inserts into sentences (`asset/js/media-files.js`, `asset/js/script.js`) and the placeholders "New URL" and "New file path" of the find & replace fields are hard-coded English

= Version 0.0.1 =

* Added: First test release of SyncPilot (private, version 0.0.1; the first public release is planned as 1.0.0 once the changes of the 0.x versions have been tested on several installs) — a fork of WP Sync DB 1.5 (itself a continuation of WP Migrate DB by Delicious Brains, last maintained in 2014) merged with WP Sync DB Media Files 1.1.4b1; functionally identical to those two plugins, rebranded and merged into one
* Changed: The Media Files addon is now part of the plugin — `SyncPilot_Media_Files` extends `SyncPilot_Base` directly and is loaded by `sync-pilot.php` right after the core class, so the migration form, the "Media Files" option and the AJAX handlers are always available; the `WPSDB_Addon` class (`class/wpsdb-addon.php`), the addon registry in the base class (`$this->addons`, `is_addon_outdated()`), the "addon out-of-date" admin warning and the second plugin header with its `version.php` are removed, as there is no separate addon whose version could mismatch
* Changed: Everything is renamed from `wpsdb` / `wp-sync-db` to `syncpilot` / `sync-pilot` — classes (`SyncPilot`, `SyncPilot_Base`, `SyncPilot_Media_Files`), functions, option names (`syncpilot_settings`, `syncpilot_error_log`), AJAX actions (`wp_ajax_syncpilot_*`, media files: `syncpilot_mf_*`), nonces, filters and actions, the `$GLOBALS['syncpilot_meta']` array, JS variables and script handles, CSS classes, the admin menu slug (`page=sync-pilot`), the text domain and the file names (`sync-pilot.php`, `class/syncpilot*.php`, `compatibility/sync-pilot-compatibility.php`, `languages/sync-pilot-en.pot`); this is a deliberate clean break, so both sides of a migration need SyncPilot and a remote site still running WP Sync DB cannot be reached
* Changed: The media files script is enqueued as `sync-pilot-media-files` — a plain rename would have given it the same handle as the core script (`sync-pilot-script`), which would have made it depend on itself and never load; the media files options form moved from `template/migrate.php` to `template/media-files-options.php` and its script from `asset/js/script.js` to `asset/js/media-files.js`
* Added: One-time import of WP Sync DB settings — on the first load `SyncPilot_Base::migrate_legacy_settings()` copies the `wpsdb_settings` option (API key, pull/push permissions, saved profiles, plugin blacklist) to `syncpilot_settings` if the latter does not exist yet, and records the time in `syncpilot_legacy_migrated`; the old option is only read, never changed or deleted, so WP Sync DB can stay installed side by side until the switch is complete
* Changed: Plugin header — author, `Requires PHP: 8.1`, `Requires at least: 6.0`, `Domain Path`; the plugin title shown in the admin is now fixed to "SyncPilot" instead of being derived from the file name; the MU compatibility plugin (`sync-pilot-compatibility.php`) is renamed, so a compatibility plugin installed by WP Sync DB (`wp-sync-db-compatibility.php`) is not replaced and keeps acting only on `wpsdb*` requests
* Changed: Help tab — the support link points to the author's website instead of the GitHub issue tracker of the original project; the demo videos are still the original screencasts of WP Sync DB and show its old user interface
* Removed: `github-updater` installation instructions and the `GitHub Plugin URI` header of the original plugin; `composer.json`, `composer.lock` and `vendor/` (only `composer/installers`) of the Media Files addon, which are not needed at runtime
* Added: Release workflow (`.github/workflows/release.yml`) — publishing a GitHub release builds `sync-pilot.zip` with the correct `sync-pilot/` root folder and attaches it to the release; the workflow refuses to build if the version in the plugin header differs from the release tag
* Verified: Pull and push between two installs on PHP 8.4 including the media files option (originals, thumbnails and WebP variants transferred with matching file sizes), "Remove local media", find & replace of the site URL, and the import of existing WP Sync DB settings
* Known issue: Not yet verified — pulling new media files (only push was tested with new files), the SQL export download, multisite (the multisite code paths of the media files class have not been run) and the WP-CLI integration
* Known issue: The code base dates from 2014 and has not been audited for PHP 8.x deprecations or warnings with `E_ALL` yet; no messages from SyncPilot appeared in the admin area of the test installs, but not every screen and code path has been exercised
* Known issue: `languages/sync-pilot-en.pot` was renamed by text replacement and not regenerated, one sentence fragment still reads "Sync DB"; the link to the find & replace documentation (`template/migrate.php`) is the unchanged link of the original plugin and probably no longer works
