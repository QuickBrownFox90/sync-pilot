== Changelog ==

= Version 0.3.0 =

* Added: The log of SyncPilot is a file of its own, `class/syncpilot-logger.php` (`SyncPilot_Logger`), instead of a text in an option. One line of JSON per entry with the time (UTC), the level (`error`, `info`), the source (`admin` for the browser of a logged-in user, `remote` for a request of the other site to a public endpoint, `cli`), the ID of the migration, the action of the request, the phase, the message and a context. It holds metadata only: names, sizes, numbers and messages. A value whose name is `sig`, `key`, `secret_key`, `nonce`, `chunk`, `form_data`, `connection_info`, `auth`, `password`, `cookies`, `authorization` or `set-cookie` is replaced by its size, a long text is cut and says how long it was, an object is its class name, a `WP_Error` its code and message, arrays are followed two levels down and 20 items wide, HTML tags and invalid UTF-8 in a message do not break the line. One entry is at most 4 KB (a context that is too long is dropped, the message stays)
* Added: The file is `uploads/sync-pilot/logs/syncpilot-log-<20 characters>.jsonl`. The name is made from the salts of the site, so it cannot be guessed and is the same on every request without being stored; the folder has a `.htaccess` that denies every request (Apache 2.4 and 2.2), a `web.config` for IIS and an `index.php`. A file is rotated before it would grow over 1 MB, three files are kept (3 MB at most), the oldest entries go first. The folder can be changed with the filter `syncpilot_log_dir` The log is read and deleted by its path only, without the right to write into the folder: the web server writes it, a command line or another user can read it
* Added: When the folder cannot be written (the uploads folder is not writable for the user of the web server, or the folder was made by another user), the entries are not lost: they go to the option `syncpilot_log_fallback` (not autoloaded, 100 KB at most, the oldest entries go first) and are shown with the log and deleted with it. The option is kept when a pull replaces the database
* Added: The level of the log is off, errors (the default) or verbose (the setting `log_level`, the filter `syncpilot_log_level`); a wrong value is the default. `SyncPilot_Logger::error()` writes at errors and verbose, `SyncPilot_Logger::info()` at verbose only.
* Added: The level of the log is chosen on the Diagnostics tab, under the title "Error Log": a selection with Off, Errors (default) and Verbose (for troubleshooting), saved when it changes (the request `syncpilot_save_log_level` takes only these three values) with the same "saved" message as the settings. German: "Protokollstufe", "Aus", "Fehler (Standard)", "Ausführlich (zur Fehlersuche)"
* Changed: The log of the older versions, the option `syncpilot_error_log`, is moved into the new log once: its end (1.5 KB) becomes one entry and the option is deleted. An autoloaded one (versions before 0.2.3) is moved on `init`, which costs no query when there is none; one that is not autoloaded is moved when the log is read or cleared
* Added: Help codes, `class/syncpilot-help-code.php` (`SyncPilot_HelpCode`, an enum with the number as its value, 35 codes). A number means one thing everywhere; the log entry carries it as `help`, the place in the code that reported it as `site` (130.02 is the second place that reports 130, numbered by hand at the call with `site: 2`) and the function and line as `at`. The log text of a code is English, short and complete in itself, without a code, a number or a fact in it (the facts are the context); it is never translated. Ranges: 1xx events of the server, 2xx media files (the `…mf` codes: 103mf is 203), 9xx reserved for the browser. `legacy()` finds the code for a number of the earlier versions (`#111`, `103mf`), `get_log_text()` answers a number that this version does not know (the other site may be newer), `format()` and `parse()` turn 130.02 into the two numbers and back. The texts for the user and the help texts come later and are read when they are needed, never when the class is loaded
* Added: The signature of every endpoint is one code, `InvalidSignature` (130), reported at ten places (the sites 1 to 10: finalize, chunk, backup, pull, initiate, verify and the three media endpoints), instead of eight numbers for the same event. The code of the user message does not change. Codes are new because the error had none: 142 `RemoteAuthRequired`, 143 `RemoteHostNotFound`, 144 `RemoteAnswerInvalid`, 145 `RemoteAnswerUnreadable`, 146 `RemoteReportedError`, 214 `MediaDownloadFailed`, and four for what ends a request: 147 `UncaughtException`, 148 `PhpFatalError`, 149 `PhpTimeLimit`, 150 `PhpMemoryLimit`
* Changed: `log_error()` takes a help code (`SyncPilot_HelpCode`), a context and the number of the site instead of a text and the data of the request; it writes the English text of the code, the facts as the context, and the function and line that called. The methods that built the text log (`save_error_log()`, `trim_error_log()`, `describe_log_data()`, `shorten_log_text()`, `cut_log_text()`) and the constants `LOG_MAX_BYTES` and `LOG_ENTRY_MAX_BYTES` are gone; their work is done by the logger (`clean()`, `shorten()`, `cut()`). "Clear Error Log" deletes the files and the option
* Added: Errors that were only answered to the browser and never logged are in the log now, each with its facts: no chunk uploaded and a chunk that cannot be read, a pull or push that this site does not allow (also for the media files), temporary tables that are missing or a table name that is not valid when finalizing, a table structure or a CREATE TABLE query that cannot be read, a dump file that cannot be written (the size, if the file is open, and the reason PHP gave), every failure of the media files (path not valid or outside the uploads folder, download, folder, moving a file, an upload without files, a list that does not match) and every failure of a request to the other site (timeout, host not found, TLS, request failed, HTTP error with its status, basic authentication, answer not serialized, plugin missing there). A failed folder or file of the media files names the nearest folder that exists, whether it is writable, its mode and owner and the user the web server runs as (`folder_facts()`), and the reason PHP gave (`last_php_error()`)
* Added: The guard of the AJAX requests, `class/syncpilot-request-guard.php` (`SyncPilot_Request_Guard`): an exception that nobody catches, a PHP fatal error, the time limit and the memory limit in a request of SyncPilot (an action that starts with `syncpilot_`) ended with the "critical error" page of WordPress (HTTP 500) and nothing in our log. They are written to the log now (help codes 147 to 150 with the message, file and line relative to the WordPress folder, the limits and the first frames of the call stack without arguments), the phase of the request (the name of the action) is in every entry of the request, and the request is answered in the way of the plugin: a logged-in user (the browser of the migration) gets the reason as JSON with `syncpilot_error`, which the progress box shows like every other error; another site that called a public endpoint gets HTTP 500 and one short sentence without any detail, because such a request can fail before the signature is checked and then comes from anyone. One place instead of a try/catch around each of the 30 handlers: it also catches what a try/catch cannot (a fatal error, the time limit and the memory limit), and 256 KB are kept back so that there is room to write the entry when the memory limit is the reason. Not active in WP-CLI and in the tests of the plugin
* Added: At the level verbose the warnings, notices and deprecations of PHP during a request of SyncPilot are in the log (help code 151, level `info`, the kind, the message and the file relative to the WordPress folder with the line), from any code: the culprit may be another plugin. Each place and kind once per request, 50 at most, so that a loop does not fill the log; a message that was suppressed with @ is not written; PHP handles the message as before (its own log, the display). At the level errors nothing changes and the handler is not registered. `log_error()` takes the level (`error`, or `info` for what is only written at verbose) as its fourth argument
* Added: The ID of a migration, for example `261112-101530-a1b2c3` (date, time, six random characters). The site whose admin page starts the migration makes it in `ajax_initiate_migration()` and gives it to the browser as `migration_id`; from then on the browser sends it with every request of the plugin (an `ajaxPrefilter` in `modules/migration.js`, so that the requests of `media-files.js` get it as well without knowing it) until the migration ends (`migration_complete_events()`). Every request that this site sends to the other one carries it in the header `X-SyncPilot-Migration`, which is not part of the signature, and the other site writes the same ID in its entries. So the entries of both sites can be put together, the field `migration` is in every entry of a migration (errors included). The ID is cleaned to letters, digits, `-` and `_` and at most 40 characters wherever it is read (`SyncPilot_Request_Guard`), because anyone can send it. `get_post_data_filtered()` leaves it out of the data that is signed
* Added: The log has a third kind of entry besides `error` and `info`: `event`, for the course of a migration. It is written at the levels errors and verbose (not at off): "Migration started" on the site that starts it (the intent, the stage and its environment), "Remote site agreed" (the environment of the other site, which it sends in its answer to the signed request; the browser does not get it) and "Migration requested by remote site" on the other site (the intent and its own environment). Three entries per migration, so every error that follows can be read with the versions and limits of both sites
* Added: The environment of a site (`SyncPilot_Logger::environment()`): the versions of the plugin, WordPress and PHP, the type of PHP and of the system, the web server, SSL, `memory_limit`, `max_execution_time`, `post_max_size`, `upload_max_filesize`, gzip, the database (version, charset, collation, `sql_mode`, `max_allowed_packet`) and the free space of the uploads folder. Names, numbers and yes/no only: no path, no address, no key, no user
* Added: A request to the other site that fails is logged with what is needed to see why (`describe_remote_response()`): how long it took (`duration_ms`), how much was sent and received (`sent_bytes`, `received_bytes`), for an answer the status and its text, the headers `content-type`, `server` and `location` (without a user name and password in the address) and a cleaned beginning of the body (`excerpt`), for a request that failed the message of cURL and its number (`curl_errno`: 28 is the time limit, 52 an empty answer, 60 the certificate). Before, the whole answer was described by its parts, the status was the only fact and there was no time. The address of the other site in an entry (`connecting_to`) has no user name and password any more (`SyncPilot_Logger::strip_credentials()`; the media files put them into an address)
* Added: The excerpt of an answer (`SyncPilot_Logger::excerpt()`, 300 bytes) is the little text of an error page and nothing else: no tags (each one is a gap between words, script and style are gone), no line breaks, a run of 32 letters, digits and `+/=_-` (a key, a signature, a token, a reference number of a firewall) is `[token]`, and serialized data or SQL, also behind a message that stands in front of them (a PHP notice before the answer), is cut off at its beginning with `[data]` or, when the answer starts with it, `[serialized data]`: such an answer holds rows of the database
* Added: At the level verbose every answered request to the other site is an entry "Remote request answered" with the scope, the status, the duration and the sizes, and without the answer
* Changed: The request `syncpilot_get_log` is split in two. It answered one text with the diagnostic info and the log behind each other. `syncpilot_get_log` answers the log and nothing else, as JSON: `{"entries": [...]}`, the oldest entry first, every entry parsed (a line that is not JSON, for example from a file that was cut, is an entry with the field `raw`, nothing is lost and the caller never has to parse); new `syncpilot_get_diagnostics` answers the diagnostic info as text (own nonce `get-diagnostics`). The Diagnostics tab has two text fields with a title each, "Diagnostic Info" and "Error Log" (the title "Diagnostic Info & Error Log" is gone; German: "Diagnoseinformationen", "Fehlerprotokoll"), and fills them with two requests; the log is shown as one JSON line per entry. `output_log_file()` is gone (`SyncPilot_Logger::entries()` replaces it). Both answers can be processed by a script without cutting a text apart, which the later views of the log (filter by migration, download, the lines of the other site) build on
* Fixed: Writing an empty line to a gzipped dump file was taken for a failure (inherited from WP Sync DB): `stow()` checked `! gzwrite()`, which is also true for 0 bytes, and set the error "Failed to write the gzipped SQL data to the file" without a reason. The log of the new version showed it (bytes 0, file open) at every gzipped backup; nothing was lost because the callers do not read the result, but the error text was set. Only `false` is a failure now, as for a file without gzip. The reason PHP gave (`last_php_error()`) is read after `error_clear_last()` at every place that uses it, so that it cannot be the reason of an earlier, unrelated error
* Added: `tests/logger.php` (`wp eval-file`, replaces `tests/error-log.php`, 60 checks): one entry from an endpoint with a 2.4 MB body (no row, no signature, no key, only names and sizes; help code, site and function), a remote answer of 3 MB with cookies, an object, a `WP_Error`, invalid UTF-8 and tags, a context that is too wide or too long, the ID of the migration, the phase and the action, the levels, 12,000 entries with 2.4 MB bodies (at most three files, each within 1 MB, the newest entries stay, every line is whole JSON, the order), the protection of the folder and the name of the file, the fallback when the folder cannot be written (the log can still be read), and the import of the old log
* Added: `tests/help-codes.php` (`php tests/help-codes.php`, no WordPress needed, 10 checks): every log text is English, short and without a code, a number, a placeholder, a tag or a full stop at its end, and its own text; the earlier numbers lead to codes that exist; `format()` and `parse()`; and the source is read: every `log_error()` names a help code and a site, no site is used twice for a code, no call uses a text, and every code is reported somewhere
* Added: `tests/guard.mjs` (`npm run test:guard`, 45 checks) with the first part of the fault injection kit, `tests/fault/sp-fault.php` (a mu-plugin for a TEST site that the test copies in and removes again; it acts only when a request of SyncPilot carries `?sp_fault=`): an exception, a fatal error, the memory limit and the time limit, each sent to a public endpoint and as a logged-in user. It checks the HTTP status and the answer (the reason and file for the user, nothing for the other site: no reason, no path), the entry in the log (help code, site, phase, source, the reason, the relative file) and that the critical error page of WordPress is not shown; that a request without a fault is answered as before, that a notice does not break the answer, and the warnings of the next entry
* Added: The second part of the fault injection kit: `tests/fault/proxy.mjs` (a proxy between the two test sites that spoils the answers: a web server error 502, a firewall 403, a request for a password 401, an empty answer, an answer that is cut, a PHP notice in front of the answer, a redirect to a web page, a closed connection, no answer at all) and `tests/browser/remote-faults.mjs` (`npm run test:faults`, 64 checks): the first site is connected to the second one through the proxy; for each fault the log must name the help code (129, 142, 144, 121, 134), the status or the number of cURL, the duration (10 s for "no answer"), the sizes and a cleaned beginning of the answer, and must hold no tag, key, password or token (and nothing of the data behind the notice); and the ID of the browser must arrive at the other site through the proxy as the header
* Added: `smoke.mjs` has a section for the Diagnostics tab (39 checks): the diagnostic info is in its own field as text, the log is in the other field as one JSON object per line without diagnostic info in it, a written entry is in it, "Clear Error Log" empties the field and the log of the site, the selection of the log level (under the title, three levels, each one saved, a value that is not a level is refused) and the page has no error
* Added: `push.mjs` checks the log of the migration (all variants): the ID and the three entries on both sites with the same ID, the environment in each, no key, address or path in them, and that the browser sends the ID with every request for the tables but not before the start

= Version 0.2.8 =

* Fixed: Cancelling a push ended with "Migration cancellation failed - Invalid content verification signature" and left the temporary tables on the other site (inherited from WP Sync DB). `ajax_cancel_migration()` signs the request to the other site with every field of the request of the browser, among them the `nonce`, but the other site does not get the nonce (it is not one of the fields it accepts) and does not count it when it checks the signature, so the signature could never match. The nonce is removed before signing, like in the requests for the tables and for finalizing. A cancelled pull was not affected
* Fixed: Cancelling a pull or a push left the table `<prefix>syncpilot_alter_statements` on the receiving site (inherited from WP Sync DB): the import creates it for the ALTER statements and drops it in its last statement, which a cancelled migration never runs. `delete_temporary_tables()` drops it as well
* Fixed: Cancelling while the media files were sent (or while the list of the files was made) sent the cancellation twice (inherited from Media Files): the two requests of `media-files.js` did not mark themselves as running, so Cancel saw no running request and sent the cancellation at once, and the answer of the media request ran `execute_next_step()`, which sent it again. The requests say that they are running now (`migration_request_running()`, put on `window` by `migration-control.js`, because `media-files.js` is a plain script and cannot reach the state of the page), like the requests for the tables
* Changed: Eighth step of the clean-up of `script.js`: the end of a migration and what the user can do while it runs are two more modules. `migration-end.js` holds `migration_complete_events()` (the message at the end, the variables of a migration are set back), `migration_complete()` (split into `finish_export()` and `finalize_tables()`) and closing the progress box (`hide_overlay()`, the button and the click on the dark layer); `migration-control.js` holds the buttons Pause / Resume and Cancel, `execute_next_step()` (every step ends with it; it lets the next step run, waits when paused, or cancels), and the request that removes what a cancelled migration made (`cancel_on_server()`, with the text from `removing_text()`). `migration_failed()` of `migration.js` takes an optional title and serves the finalizing and the cancellation as well, so the code for "title, text, class, flag, end" exists once. The four placeholders `window.migration_complete`, `window.migration_complete_events`, `window.execute_next_step` and `window.migrate_table_recursive` in `script.js` are gone: the modules put the functions on `window` when the page is ready (`media-files.js` and the steps call them by name). The global `progress_msg` that was set by accident is local now. `script.js` shrinks from about 1,270 to about 980 lines. Nothing changes for the user
* Changed: Ninth step of the clean-up of `script.js`: the connection to the other site is `modules/connection.js` (`prepare_connection()` at the start of the page: the lists of tables as the page had them, the backup options, a saved profile connects by itself; `init_connection()`: the box that moves between the lists of pull and push, the buttons and links around it). Its two requests to the other site were copies of each other (a typed connection and a saved profile): the error answer, the failed request, the locked box with the notices (`show_connection()`), the text "establishing connection" and the three lists of tables and post types (`build_select()`, instead of three loops each with its own copy of the options) exist once now; what is different stays apart: `fill_lists_from_profile()` selects what the profile saved, `fill_lists()` and `fill_replace_rows()` fill a new profile. The checks of what is typed are `connection_info_error()` (a message or an empty text, instead of a chain of flags), `validate_url()` moved with them. The variables `connection_info_box` and the six lists are variables of the module instead of the closure of the page; `script.js` shrinks from about 980 to about 230 lines. Nothing changes for the user
* Added: `node tests/browser/push.mjs --yes --cancel` (with `--pull` for the other direction, with `--backup` for the cancellation in the backup stage): the migration is started with slowed requests, Cancel is clicked while it runs, and it has to end with "cancelled" and without an error message, no `_mig_` or `_old_` table is left on the receiving site, its data was not replaced, and the backup file of the cancelled migration is removed. It found the two errors above; before, only the cancellation of an export was tested With `--media` Cancel is clicked while the files are sent, and the cancellation must be sent exactly once (it was sent twice before the fix above)
* Changed: `push.mjs` drops temporary tables (`_mig_`, `_old_`) of a failed or cancelled migration when it puts a site back to the reference; the backup does not contain them, and they stayed
* Added: `tests/browser/connection.mjs` (`npm run test:connection`, 31 checks): the six messages for what is typed (nothing, one line, no address, a key of the wrong length, the address or the key of this site; each its own message and no request), a connection for a push (locked box, name of the profile, new URL and path, the lists, the row for the scheme), switching to pull (the box moves, the rows of find and replace are swapped, the list of tables) and to export, unlocking the box (the question, OK), and saved profiles that connect when the page is loaded (push and pull with the tables and the tables for the backup they saved, and a wrong key: the message of the other site, nothing locked, no spinner). The part for saved profiles was not covered by any test before and is the second copy of the request. Nothing is migrated; the settings are put back at the end
* Changed: The version is raised to 0.2.8 in the plugin header, in `$GLOBALS['syncpilot_meta']`, in the MU compatibility plugin and in the README

= Version 0.2.7 =

* Added: A new profile gets a row for the scheme in "Find and replace" when the two sites differ, one with http and the other with https (`add_scheme_row()` in `modules/replace-rows.js`, called when the connection to the other site is verified): the plain `http://` to `https://`, or `https://` to `http://` going the other way. Every address is turned, not only the one of the receiving site, so the other domains of a multisite follow, mixed content is set right going to https, and a local site without SSL does not load its own files from https addresses, which the browser blocks. External links, fonts and embeds are turned as well; the row can be removed in the form. The row stands behind the rows for the URL and the path, because the replaces run in the order of the rows. A loaded profile keeps its rows, and connecting again replaces the row instead of doubling it. Nothing changes when both sites use the same scheme
* Added: `push.mjs` checks the row for the scheme after the connection (push and pull): its content and its place behind the URL and the path, and that there is none when both sites use the same scheme
* Fixed: Downloading the media files of the other site ignored the setting "Enable SSL verification" (inherited from Media Files): `download_url()` called `wp_remote_get()` without `sslverify`, so the certificate was always checked, and a pull with media files from a site with a self-signed certificate ended with "Could not download file: ... cURL error 60" for every file, although the check was switched off in the settings and the connection itself worked. It uses `verify_ssl()` like every other request to the other site now
* Changed: Seventh step of the clean-up of `script.js`: `modules/migration.js` holds the request that starts the migration (`initiate_migration()`) and the loop over the tables (`migrate_table_recursive()`, split into `start_tables()`, `start_migrate_stage()` (after a backup), `start_final_steps()`, `show_table_text()`, `table_request_data()`, `send_table_request()`, `table_answered()` and `count_progress()`). The five places that ended a migration with an error (title, text, class, flag, end) are one function, `migration_failed()`, and the three `console.log()` lines of a failed request are in `request_problem()`. What the loop remembers (the position, the rows of the tables, the sum, the progress) is one object in the module instead of six variables in the closure of the answer; the globals `last_table`, `gzip` and `row_information` that were set by accident are local now. `migrate_table_recursive` is put on `window` by `init_migration()`. `script.js` shrinks from about 1,520 to about 1,270 lines, the click handler `run_migration()` from about 340 to about 80 lines. Nothing changes for the user
* Changed: The test browser accepts the self-signed certificate of a test site (`--ignore-certificate-errors`), and `login()` sets the secure cookie when the site uses https (WordPress asks for it in the admin of an https site). The second test site runs with https now
* Changed: The version is raised to 0.2.7 in the plugin header, in `$GLOBALS['syncpilot_meta']`, in the MU compatibility plugin and in the README

= Version 0.2.6 =

* Fixed: On a fresh installation (and on any site where WordPress 6.7 or later is used) the admin showed two notices when the plugin was activated: "Translation loading for the sync-pilot domain was triggered too early" and, on PHP 8.1 or later, "Automatic conversion of false to array is deprecated" (`class/syncpilot.php`). The constructor of the base class translated a text (`invalid_content_verification_error`) on `plugins_loaded`, before the text domain is loaded on `init`; the text is set by `set_translated_texts()` on `init` with priority 20 now, and every place that uses it is a request handler or the admin page, which run later. The constructor of `SyncPilot` set `max_request` on the option `syncpilot_settings` before it existed (`get_option()` gives `false` then); it is made an array first. The notices were gone after the first migration only because the option existed by then; nothing else changes
* Fixed: Determining the media files could end with the "critical error" page of WordPress (HTTP 500) and the message "Error while attempting to determine which media files to migrate. (#101mf)" (inherited from Media Files). `get_local_media()` reads the sizes of all files in the uploads folder, and `getSize()` throws an exception for an entry that cannot be read (a link that leads nowhere, a file that is removed while the folder is read), as does a subfolder that cannot be opened; nothing caught it. Both are skipped now. A link that leads nowhere is left out of the list, a folder that cannot be opened is listed but not entered
* Changed: Fourth step of the clean-up of `script.js`: the click on "Migrate DB" is a named function, `run_migration()`, and the button is bound to it (`$( '.migrate-db-button' ).click( run_migration )`), instead of a function of about 580 lines inside the call. * Security: The Media Files sync accepted paths from the other site without checking them. When a site received media files (`respond_to_push_request()`), the file was written to the uploads folder plus the path that the sender named, so anyone who knew the key could write any file, with any name, anywhere the web server may write — `../../wp-content/plugins/x/shell.php` gives code execution on the receiving site. A second check, `is_inside_uploads()`, makes sure with `realpath()` that the destination is inside the uploads folder, symbolic links included. A request with one bad path writes nothing at all. New messages: "The path of the media file is not valid: %s (#111mf)", "The list of media files does not match the uploaded files. (#112mf)" and "The media file would end up outside the uploads folder: %s (#113mf)"

= Version 0.1.1 =

* Security: **Both sites must run 0.1.1** — the request signature changed and 0.1.0 (or older) and 0.1.1 reject each other's requests with "Invalid content verification signature". The old signature was HMAC-SHA1 over all fields glued together without a separator, so a value could be moved from one field to another, and a recorded request could be replayed at any time. The new signature is `<timestamp>.<HMAC-SHA256>`; the HMAC covers the timestamp and every field with its name and the length of name and value, it is compared with `hash_equals()`, and a request is only accepted within 10 minutes of its timestamp (filter `syncpilot_signature_window`; the clocks of both servers must be roughly right)
* Security: The certificate of the other site is checked now — `remote_post()` passed `sslverify => false` on every request, and the setting "Enable SSL verification" was saved but never used. It follows the setting now, and new installations have it switched on (existing installations keep what they had stored). With the check on, a certificate error is reported with the new message "The TLS certificate of the remote site could not be verified … (#139)". The explanation of the setting in the Settings tab is rewritten, as it said that the check is off by default
* Security: The connection test no longer falls back from https to http when "Enable SSL verification" is on. Before, any failure of the https request — also one forced by someone on the network — switched the whole migration to unencrypted http and only showed the notice "SSL Disabled". With the check off the fallback and the notice stay as they were, so local sites without a certificate keep working
* Security: `unserialize()` creates no objects any more (`allowed_classes => false`, new helper `safe_unserialize()`) for answers of the other site, for `primary_keys` of a request, for media data and for every value that find & replace goes through. A manipulated answer or a manipulated value in the source database could otherwise start `__wakeup()` or `__destruct()` of any installed class (object injection). Find & replace now handles all objects like the objects of classes that are not loaded: the `(array)` cast keeps the property names, and the object is built again with its class name. Values in the old `Serializable` format (`C:…`) cannot be rebuilt without their class and are left unchanged
* Security: Text from the other site that the admin page shows with `.html()` goes through `syncpilot_sanitize_html()`: only `a` (with `href` to `#`, a relative path or http(s), plus `class`), `br`, `strong`, `b`, `em`, `i`, `u`, `code`, `p`, `ul`, `li`, `h3`, `span` and `div` (with `class`) stay, scripts, styles, event handlers and `javascript:` links are removed; the parser is `DOMParser`, which neither runs scripts nor loads images. Values of the other site that are plain text (plugin version, URL, table prefix, uploads path, media files version) are set with `.text()`
* Security: Export files (`…-migrate-…sql`, `…sql.gz`) in `uploads/sync-pilot/` can no longer be downloaded directly — an `.htaccess` (Apache) and a `web.config` (IIS) deny them, they are only handed out by the plugin after a login; the rules are also written into folders that already exist. Backups (`…-backup-…`) stay reachable, because the page links to them after a migration. The random part of the file names has 32 instead of 5 characters (`random_bytes()`), so that names cannot be guessed; older files keep working and are recognized when they are downloaded. The listing of the folder is switched off
* Security: Keys are generated with `random_int()` instead of `rand()`, and the character set contained no `w` and the `q` twice, now it has all 64 characters; keys that already exist are not changed
* Verified: 36 checks on PHP 8.3 and 8.4 for the signature (valid, wrong key, changed or added field, value moved between fields, old format, one hour old or in the future, garbage), `unserialize()` (no `__wakeup` or `__destruct` runs, arrays still work, objects in find & replace keep class and properties), the certificate handling (error message, no fallback with the check on, fallback with it off), keys and dump names; 18 checks of the HTML sanitizer in Chromium with script, `onerror`, `javascript:`, `data:`, `style`, `iframe`, form and broken markup, none of which ran or stayed, and with the real messages of the plugin, which stay intact; the rules of the dump folder against Apache: exports 403, backup 200
* Verified: Push and pull between two test installs with the new signature (client on the PHP 8.4 CLI, server on Apache with PHP 8.4, `WP_DEBUG` on both sides) ran without any PHP message from the plugin on either side; afterwards 86 of 87 tables had the same checksum as before (all posts, `wpml_language_switcher` and the font posts byte-identical), only `wp_options` differs in WordPress' own transients, the schedule (`cron`) and the rewrite rules; the remote site accepts a request with a valid signature and refuses — over real HTTP — the old signature, a valid but one hour old signature, a valid signature with a changed field and a missing signature
* Fixed: `finalize_migration()` ran `DROP TABLE` for every real table before it renamed the temporary table to its name, so a temporary table that was missing (a chunk that was lost) cost the real table. The order was suggested by the author of the plugin and is now: first it checks that all temporary tables exist and stops with the new message "These temporary tables do not exist … No table was replaced (#140)" if one is missing, then ONE `RENAME TABLE` renames all old tables to `_old_<name>` and all temporary tables to their final names (all renames succeed or none does, and the site never sees half a database), then the preserved options and the constraints are written, and only when all of that has worked the `_old_` tables are dropped. If a step after the renaming fails, the `_old_` tables stay as a backup; the next migration removes `_old_` tables it finds. Table names and prefixes with a backtick are refused with the new message (#141)
* Verified: `finalize_migration()` on throwaway tables (13 checks, PHP 8.3 and 8.4): everything works including a table that does not exist at the target yet; a missing temporary table stops with #140 and leaves every table untouched; an error after the renaming keeps the `_old_` tables with their data; the next run removes such leftovers and works; a backtick in a table name or prefix is refused. Against the real second site (Apache, PHP 8.4): a normal push and pull leave no `_old_` or `_mig_` table and give the same checksums as before (only `wp_options` differs in transients, schedule and rewrite rules); a push after which a temporary table was removed on the remote side was refused with #140, the 86 remaining temporary tables were still there and no real table, no `_old_` table and no data had changed
* Fixed: **0.1.0 breaks the whole admin page as soon as the migration form is shown.** `template/migrate-progress.php` called `$wpdb->get_prefix()`, a method that does not exist in WordPress, in the label of the progress bar. That is a fatal error: PHP stopped after the form, WordPress ended the page, and the footer with all SyncPilot scripts (`common.js`, `hook.js`, `script.js`, `media-files.js`) was never sent, so nothing on the page reacted — no radio button, no connection field, no "Migrate DB" button. The profile selection, the Settings tab and the export did not show it, because they do not render this template. The label shows the table prefix again (`wp_options`); the template had static text before 0.1.0
* Verified: The three views of the plugin page (profile selection, migration form for a new profile, migration form for a saved profile) answer with HTTP 200, a complete page, the four SyncPilot scripts and no PHP message; in a real browser (headless Chromium, logged in as an administrator, desktop size, real mouse clicks) the tabs switch, "Pull" and "Push" show the connection field, a pasted connection info is verified against the other site and fills in the search and replace rows, and a complete push through the interface runs to "Pushing to … completed" in 52 seconds without a JavaScript error or an HTTP error; afterwards the remote site has the same number of rows in all tables except `wp_options`, where exactly the 53 transients are missing that the form excludes by default, and no `_mig_` or `_old_` table is left
* Known issue: The signature does not protect against a replay within the 10 minutes, and `transfer_chunk()` still discards the answer of the remote site when no error was recorded on the local side (inherited from WP Sync DB 1.5; the damage it could do in `finalize_migration()` is gone)
